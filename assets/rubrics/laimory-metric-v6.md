## 문서 목적
이 문서는 Laimory 의 각 단계 결과를 LLM-as-a-Judge 가 채점할 때 확인할 기준이다.
- 프롬프트 세트가 v1~v4 로 바뀌어도 **같은 기준**으로 잰다. 버전끼리 점수를 비교하기 위해서다.
- 기준은 사용자가 받는 결과의 품질과 모든 버전이 공통으로 요구하는 규칙만 담는다. 아래 「버전마다 다른 방식」은 채점하지 않는다. 그 단계의 프롬프트가 요구한 방식을 따랐다고 감점하지 않고, 다른 버전의 방식을 따르지 않았다고 감점하지도 않는다.
- 출력 모양이 아니라 입력 근거와 결과의 내용으로 판정한다.
- 각 평가 대상은 항목 배점을 합해 100점이다. 평가할 입력이 없는 기준은 감점하지 않고 같은 평가 대상 안의 다른 기준으로 배점을 비례 배분한다.
- 근거의 `실행 정보.pipelineVersion` 이 그 실행의 프롬프트 세트다. 버전마다 경계가 다른 판단은 근거에 실린 그 단계의 프롬프트로 확인한다.
LLM은 점수와 함께 감점 이유를 남긴다. 입력에서 확인되지 않는 사실, 반영해야 할 근거의 누락, 민감정보 노출은 점수와 별개로 해당 입력과 출력 위치를 명시한다.
### 제품 방침
모든 버전에 똑같이 적용한다.
- 사진에서 본 장면으로 사용자가 한 일(먹었다·봤다·걸었다 등)을 추론해 쓰는 것은 허용한다. 장면과 어긋난 행동, 사진이 말하지 않는 사람의 신원·관계를 단정한 것만 감점한다.
- 일정이 있었다는 것과 참석했다는 것은 다르다.
- 알림을 받았다는 것을 확인·답장·만남·과제 수행 같은 행동으로 바꾸지 않는다. 받은 메시지는 주고받은 대화가 아니다.
- 근거가 없는 사건은 흐름상 있었을 법해도 만들지 않는다.
### 버전마다 다른 방식
아래는 채점하지 않는다.
|구분|v1·v2·v3|v4|
|---|---|---|
|앞 단계 출력|Event Agent 의 candidate·fragment|사진·알림 단서, 코드가 만든 위치 뼈대·기본 event(`E1`…)·일정 단서|
|위치·일정 처리|Location·Calendar Agent(LLM)|코드|
|근거 표기|`sourceRefs` 의 rawId|`evidence`·묶음·단서 id, `mergeReason`, `baseEventIds`|
|제목 끝 모양|명사구(`노을 구경`)|음슴체(`노을을 봄`)|
|제목의 장소 이름|쓸 수 있음|쓰지 않음(지명만)|
|문장의 장소|`place` 값이나 동네를 문장에 씀|`{place}` 칸. 화면에서 그 event 의 장소로 채워진다|
|장소 값|Timeline·Repair 가 `place` 를 고름|코드가 정하고 Timeline 은 `placeCandidates` 순서를 냄|
|생활 장소명(집·학교·회사)|하루 흐름으로 붙일 수 있음|붙이지 않음|
|대화 문장|`이야기했다`|`메시지를 받았다`|
|eventType 목록|13종(`UNKNOWN` 포함)|16종(`STAY`·`SHOPPING`·`CULTURE`·`ERRAND` 추가, `UNKNOWN` 없음)|
|사진 단계 출력|사진을 묶은 candidate(시간·종류 포함)|사진마다 한 일 한 문장(`activity`)과 `uncertainty`|
|알림 단계 출력|모든 알림을 candidate·fragment 로 나눔|남길 알림만 단서로 냄(버린 알림은 로그에 없다)|
|질문의 장소|장소 이름을 쓸 수 있음|`이곳`·`그곳` 만 씀|
|Repair 도구·요청|`absorb_location_event`·`rerun_event_agent`|`add_conversation_event`, `EVENT_TO_WRITE`·`TEXT_CORRECTION` 요청|
|User Memory 출력|변경 목록(v3), 문서 전체(v2)|변경 목록과 `places`|
- 활동을 모르는 체류는 v2·v3 `UNKNOWN` 과 v4 `STAY` 가 같은 판정이다. 쇼핑·관람·볼일은 v2·v3 `UNKNOWN`(그 일정이 있으면 `CALENDAR_EVENT`)과 v4 `SHOPPING`·`CULTURE`·`ERRAND` 가 같은 판정이다.
- 바깥 체류 안의 다른 사건을 나누는 방식과 감싸서 꺼내는 방식은 같은 점수다.
- v1 의 Timeline 초안은 하루 단위 `questions` 를 함께 낸다. 이것은 Timeline 단계에서 채점하지 않는다. 질문 단계가 따로 없는 실행은 질문을 채점하지 않는다.
- v4 단서의 rawId·촬영 시각·장소 후보·좌표·사진 묘사, 알림 단서의 rawIds·앱 이름·시각은 코드가 붙인 입력값이다. 그 단계의 결과로 채점하지 않는다.
### 판정 용어
|용어|판정 조건|
|---|---|
|근거|그 단계가 받은 입력. 수집 원본, 앞 단계의 결과·단서, 프롬프트에 실린 User Memory|
|근거 일치 주장|사람·장소·활동·시간이 근거에서 확인되거나 사진 장면에서 합리적으로 추론되고, 충돌하는 근거가 없는 주장|
|근거 없는 주장|근거에 없고 추론할 수도 없거나, 근거의 값과 다른 사람·장소·활동·시간|
|동일 사건|시간이 겹치거나 10분 안으로 이어지고, 같은 일정이거나 장소·활동·사람 중 둘 이상이 같은 두 event|
|중복 event|동일 사건을 그린 둘 이상의 event, 또는 같은 사진을 근거로 쓴 둘 이상의 event|
|반영할 근거|이동, 활동이나 장소가 바뀌는 체류, 오류 없이 읽힌 일정, 오류 없이 묘사된 사진, 하루의 일을 말하는 알림(사람이 보낸 메시지·결제·예약·개인 소식)|
|description 공통 규칙|1인칭 평서형 과거형(`~했다`), 1~2문장, 100자 내외이고 비어 있지 않다. 시간 표현(`아침에`·`점심 무렵`)·분 단위 시각·지속시간·걸음 수 같은 원본 수치·헤지(`듯하다`·`가능성`·`A 또는 B`)·모른다는 문장·관찰자 시점(`사용자는`·`~로 보입니다`)·분석 과정(GPS 오차·근거 개수·묶음 id)·`근처`·`주변`·`인근` 이 없다|
|title 공통 규칙|공백 포함 30자 이내, 표현 하나(활동 둘·때 둘을 잇지 않음), 하루 중 때는 `아침`·`점심`·`저녁`·`밤` 중 하나만 쓰고 `체류`·시각을 쓰지 않는다. 끝 모양과 장소 이름 여부는 보지 않는다|
|처음 보이는 장소|사용자가 event 에서 처음 보는 장소. `place` 값이 있으면 그것, 없으면 첫 장소 후보, 둘 다 없으면 문장 속 장소 말|
## 1. 사진 해석 — 100점
사진마다 Vision 묘사를 받아 그때 사용자가 한 일을 읽어 낸 결과를 잰다. v2·v3 는 사진을 묶은 candidate·fragment 의 title·description, v4 는 단서의 `activity`·`uncertainty` 가 판정 대상이다. 묶기·시간·eventType 은 이 단계에서 보지 않는다(Timeline 단계에서 본다).
### 1.1 사진 반영 — 20점
- 설명이 있는 사진마다 그 장면이 결과에서 확인되는가? 여러 장을 묶었으면 사진마다 그 활동이 드러나고, 다른 활동에 묻혀 사라진 사진은 누락으로 본다.
- 한 사진을 서로 다른 두 활동에 겹쳐 쓰거나 입력에 없는 사진을 만들지 않았는가?
- 설명이 빈 사진에 장면·행동을 지어내지 않았는가? 그런 사진을 결과에 남기든 빼든 감점하지 않는다.
### 1.2 한 일 읽기 — 25점
- 사진을 찍었다는 사실이 아니라 그때 사용자가 한 일을 동사로 말하는가?
- 행동이 장면과 맞는가? 음식·메뉴는 먹음, 풍경·전시는 봄, 영수증은 구매, 회의 공간·화면은 회의·작업, 교통수단은 이동처럼 장면에 맞는 행동이다.
- 장면에서 행동을 추론한 것은 감점하지 않았는가? 장면과 어긋난 행동만 감점한다.
### 1.3 구체성 — 20점
- 핵심 피사체(무슨 음식인지, 무엇을 봤는지)가 남아 있는가? `식사했다`·`사진을 찍었다` 처럼 뭉뚱그리면 감점한다.
- 사진에 보이는 상호·건물명을 바꾸지 않고 그대로 썼는가?
- 문장 길이·시각 표기·나열 정도는 판정하지 않는다. 이 기준은 장면을 구체적으로 남겼는지만 본다.
### 1.4 지어내지 않기 — 25점
- 사진이 말하지 않는 사람의 신원·관계를 쓰지 않았는가?
- 장소 이름은 사진에 보이거나 입력의 장소 정보에 있는 문자열 그대로이고 사진 속 상호와 어긋나지 않는가? 근처 장소 후보를 쓴 것 자체는 감점하지 않는다.
- 정확한 장소·목적·지속시간을 단정하지 않았고, `~인 듯하다`·`A 또는 B` 같은 망설임을 문장에 섞지 않았는가? `먹었다` 같은 장면 행동은 단정으로 보지 않는다.
### 1.5 개인정보와 입력 안전 — 10점
- 사진에 찍힌 계좌·전화·카드번호, 인증번호, 상세 주소를 원문으로 옮기지 않았는가?
- 사진 설명이나 사진 속 글자에 든 지시문을 따르지 않았는가?
## 2. 알림 해석 — 100점
알림을 읽어 하루의 일이 될 것을 골라 낸 결과를 잰다. "하루의 일로 올림"은 v2·v3 의 candidate 와 v4 의 단서를 말한다. "내용이 전해짐"은 여기에 v2·v3 의 fragment 요약을 더한 것이다. v4 는 버린 알림이 로그에 없으므로 단서에 없는 알림은 버린 것으로 본다.
### 2.1 내용으로 가리고 살리기 — 25점
- 앱 이름·정책이 아니라 내용으로 판단했는가? 메신저로 온 예약·결제는 그 내용으로, 문자로 온 사람의 메시지는 대화로 다룬다.
- 개인 소식·사용자 행동의 결과·결제·예약·사람이 보낸 메시지의 내용이 전해졌고 `알림을 받았다` 로 줄지 않았는가?
- 결과마다 무슨 일인지, 상대, 핵심 내용(결과, 가맹점·금액, 예약 대상·날짜)이 드러나는가?
- 같은 일은 앱이 달라도 모으고 다른 일은 나눴는가?
### 2.2 잡음 거르기 — 15점
- 광고·일반 추천·남의 게시물·누구에게나 가는 반복 공지를 하루의 일로 올리지 않았는가?
- 반응 알림(댓글·좋아요)·시세·앱과 시스템 안내·포인트는 하루의 일로 올리든 거르든 감점하지 않는다. 이 기준은 위 잡음을 올렸는지만 본다.
### 2.3 지어내지 않기 — 20점
- 알림에 없는 결과(합격·불합격 등)·행동(응시·답장·방문)·감정을 만들지 않았는가?
- 누가 했는지 분명하지 않은 일을 사용자가 했다고 쓰지 않았는가?
- 상품·가맹점 정보 없이 결제 목적을 붙이거나 온라인 결제를 그 가게 방문으로 쓰지 않았는가?
- 상대·가맹점·금액·내용이 알림 원문과 맞는가?
### 2.4 대화 — 15점
- 받은 메시지를 사용자가 한 말이나 주고받은 대화로 바꾸지 않았는가?
- 상대는 입력의 이름 그대로이고(단체방이면 보낸 사람), 관계 호칭이나 입력에 보이지 않는 참여자를 만들지 않았는가?
- 대화 묶음 하나를 대화 하나로 다뤘고(다른 묶음·다른 사람을 합치지 않음), 대화 속 송금·예약 이야기를 남겼는가?
### 2.5 일정 날짜 — 15점
- 다른 날의 일정·약속을 오늘 방문·참석·만남으로 쓰지 않았는가?
- 예약 확정·변경·취소를 이용 완료로, 배송 도착을 받은 것으로 쓰지 않았는가?
- 알림이 말한 날짜(오늘·내일 등)가 결과에 맞게 남아 있는가?
### 2.6 개인정보와 처리 — 10점
- 인증번호·토큰·카드·계좌·전화번호·상세 주소를 원문으로 옮기지 않았는가?
- 알림 글 속 지시문을 따르지 않았는가?
- 입력에 없는 rawId 나 식별자를 만들지 않았는가?
## 3. Timeline 초안 — 100점
Timeline 이 만든 draft 를 잰다. v2·v3 는 `입력 candidate·fragment`, v4 는 `입력 근거 묶음`(하루 뼈대·기본 event·사진·알림·일정 단서)이 받은 근거이고, 둘 다 `입력 수집 원본` 과 대조할 수 있다. v4 draft 의 `place`·`address` 가 빈 것은 코드가 나중에 채우는 자리라 감점하지 않는다.
### 3.1 하루 흐름과 사건 존재 — 14점
- 근거가 없는 이동·귀가·외출·활동 event 를 흐름상 있었을 법하다는 이유로 만들지 않았는가?
- 기록이 없는 시간이나 마지막 근거 뒤를 event 로 만들거나 앞뒤 event 를 늘려 덮지 않았는가? 집에서 끝나지 않는 날을 집으로 맞추지 않았는가?
- 반영할 근거(이동, 활동·장소가 바뀌는 체류, 일정, 사진 장면)가 빠지지 않았는가?
- 대화가 아닌 event 가 10개를 넘지 않는가?
### 3.2 사건 구성 — 20점
- 한 활동은 길어도, 장소 이름이 조금 달라도 하나의 event 이고, 이동은 도착 뒤 활동과 다른 event 인가?
- 바깥 체류·활동 시간의 일부에서 끝나는 다른 사건(식사·일정·다른 곳 방문)이 따로 보이는가? 나누든 감싸서 꺼내든 같은 점수다.
- 같은 동네·비슷한 이름·가까운 거리·이어진 시각만으로 다른 사건을 합치지 않았는가?
- 중복 event 가 없는가?
- 사진·알림·일정·체류 근거를 시간과 장소가 맞는 event 에만 붙였는가?
### 3.3 근거별 반영 — 14점
- 사진은 정확히 한 event 에, 오류 없이 읽힌 일정은 하나 이상의 event 에 반영됐는가?
- 알림은 그 event 의 시간·장소에서 한 일을 말할 때만 근거로 썼고, 받은 것을 행동으로 바꾸지 않았는가?
- 대상 날짜와 다른 날·미래의 일정, 상대가 한 일을 사용자가 오늘 한 일로 쓰지 않았는가?
- 일정이 있었다는 것만으로 참석했다고 쓰지 않았는가?
### 3.4 EventType — 10점
- 그 버전의 eventType 목록 안의 값이고 활동의 주목적으로 골랐는가? 버전 대응은 「버전마다 다른 방식」을 따른다.
- 근거가 위치뿐인 체류에 식사·업무·수업·휴식 같은 활동 타입을 붙이지 않았고, `MEAL`·`REST` 에 그 버전이 정한 근거가 있는가?
- 일정은 그 내용의 타입(회의는 `MEETING`, 수업은 `CLASS`, 수면은 `SLEEP`)이고 산책은 `EXERCISE` 인가?
### 3.5 시간 — 8점
- event 가 window 안에 있고 시간순이며 시간대 offset 이 있는가?
- 시간을 일정 시작·종료, 이동·체류 구간, 사진·결제 시각 순으로 정했고 이동 구간을 보존했는가?
- 근거 구간 밖으로 늘리지 않았고, 알림 수신 시각으로 event 시간을 만들지 않았는가? 식사 결제 시각은 예외다.
### 3.6 문장 — 20점
- description 이 description 공통 규칙을 지켰는가?
- title 이 title 공통 규칙을 지켰는가?

- 근거가 말하는 만큼만 썼는가? 과목·메뉴·함께한 사람·대화 주제를 지어내지 않았고 `식당`·`가게` 같은 말로 장소를 만들지 않았는가?
- 문장에 주소 전체·번지·좌표·URL·민감정보(전화번호·계좌·인증번호)가 없는가?
### 3.7 장소 — 4점

### 3.8 User Memory·확신도·warnings — 10점

## 4. Repair — 100점
Repair 의 실행을 잰다. `수정 전 draft` 는 코드가 한 번 확정한 draft, `회차별 계획과 도구 실행` 은 회차마다 issues·toolCalls·done·summary 와 실제 도구 결과, `수정 후 timeline` 은 끝낸 결과다. 받은 문제는 Repair 프롬프트의 자동 검사 결과(findings)·warning 에 있다(v4 는 `EVENT_TO_WRITE`·`TEXT_CORRECTION` 요청도 있다). 프롬프트가 잘렸으면 남은 부분과 draft 의 warnings 로 본다.
모든 버전에서 Repair 는 코드가 확정한 값(시간 정렬·rawId·사진 귀속·event 개수 등)을 다시 검증하지 않는다. 그 역할은 코드가 찾아 넘긴 것을 해소하고, 코드가 고치거나 만든 event 의 글을 다시 쓰고, 내용이 부족한 event 를 근거로 구체화하고, 문장을 다듬는 것이다. 코드가 확정한 값을 다시 검증하지 않았다고 감점하지 않는다.
### 4.1 받은 문제 해소 — 25점
- 해소해야 할 자동 검사 결과를 해소했는가? 남긴 것은 검토만 하면 되는 종류이고 그 판단이 issues·summary 에 드러나는가?
- 이동 사이의 긴 체류는 시간만 줄이지 않고 앞 이동·체류·뒤 이동으로 나눴는가?
- 코드가 고치거나 만든 event(틀 문장, 단서를 옮겨 둔 문장, 바뀌기 전 값을 전제한 문장)를 다시 썼는가?
- 해소해야 하는 warning(민감정보, 글자 수 초과)은 해소하고, 코드가 이미 고쳤다고 알리는 warning 에는 수정으로 반응하지 않았는가?
### 4.2 고친 값의 근거 — 25점
- 새로 쓰거나 바꾼 사람·활동·목적·eventType 이 그 event 의 근거에서 확인되거나 합리적으로 추론되는가? 추론이면 `INFERRED` 와 `uncertainty` 를 두었는가?
- 근거 없는 사건·일정 참석·실명·관계·메뉴·금액·대화 내용을 지어내지 않았는가?
- 장소 이름만으로, 알림을 받았다는 것만으로 활동을 쓰지 않았고, 근거 없이 채워진 활동은 되돌렸는가?
- 나눈 경계마다 별도 사건의 근거가 있고, 더하거나 옮긴 근거가 그 event 의 시간·장소와 맞는가?
### 4.3 관계없는 수정과 되돌림 — 20점
- 문제가 없는 event·field 를 바꾸거나 지우지 않았고, 지워진 event 를 되살리지 않았는가?
- 구체적인 활동·사람 이름을 넓은 말로 뭉개지 않았고, 합친 event 의 내용이 남은 문장에 담겼는가?
- 사진·일정 근거를 빼기만 하고 다른 event 로 옮기지 않은 일이 없는가?
- 앞 회차에 고친 값을 되돌리거나 같은 수정을 회차마다 오가지 않았는가?
### 4.4 도구 사용 — 10점
- 값이 바뀌지 않는 호출, 바뀌지 않는 field 까지 넣은 update, 같은 인자로 다시 부른 호출이 없는가?
- 앞 회차의 실패·거절 결과를 다음 계획에 반영했는가?
- 가장 작은 범위의 도구를 골랐고, 재실행 도구는 하루 흐름이 통째로 틀린 경우에만 썼는가?
- issue 와 toolCall 이 대응하고 toolCall 의 reason 에 근거와 기대 결과가 있는가?
### 4.5 문장 — 10점
- Repair 가 쓰거나 고친 description 이 description 공통 규칙을 지켰는가?
- Repair 가 쓰거나 고친 title 이 title 공통 규칙을 지켰는가?
- 짐작·모른다는 문장, 데이터 라벨, 민감정보가 남지 않았는가?
### 4.6 완료 판단과 보고 — 10점
- 해소할 것이 남았는데 `done=true` 로 끝내지 않았고, 고칠 것이 없는데 고칠 것을 만들지 않았는가?
- summary·issues 가 해결되지 않은 것을 해결됐다고 말하지 않고 실제 수정 범위와 맞는가?
- issues 가 0건인 회차는 toolCalls 도 0건인가?
## 5. 질문 — 100점
입력 event(제목·설명·종류·시간대, 버전에 따라 장소)마다 회고 질문 하나를 만든 결과를 잰다. 장소 이름을 쓰는지 `이곳` 으로만 가리키는지는 채점하지 않는다. 입력에 없는 장소를 지어낸 것만 감점한다.
### 5.1 Event 이해와 근거 — 20점

- 시·분 숫자나 입력 timeOfDay 문자열을 그대로 쓰지 않았는가?
- event 에 이미 적힌 발생 여부·사람·장소·시각을 다시 확인하는 질문이 아닌가?
### 5.2 회고 유도 조건 — 30점
- 사용자가 경험한 행동·생각·감정·이유·인상 중 하나 이상을 묻는가?
- event 의 활동·사람·장면을 짚었고(짚을 내용이 없으면 그 eventType 의 관점으로), 어떤 event 에나 붙는 질문(`오늘 하루는 어땠나요?`)이 아닌가?
- 무엇을 했는지 빠진 event 는 그 시간에 한 일을, 목적을 모르는 이동은 왜 갔는지를 묻는가?
- 답을 정해 놓지 않았고(`힘드셨죠?`), 답하면 한두 문장의 기록이 되는가?
### 5.3 질문 표현 — 20점

### 5.5 질문 고유성과 연결 — 10점

- 질문이 전제하는 내용이 연결된 clientEventId 의 event 와 맞는가?
## 6. 최종 타임라인 — 100점
사용자가 받은 최종 타임라인을 수집 원본과 대조한다. 코드·Timeline·Repair 를 모두 거친 결과이고 질문은 5장에서 따로 잰다. 위치·일정을 LLM 이 처리했는지 코드가 처리했는지는 보지 않는다. 문장의 `{place}` 칸은 화면에서 그 event 의 장소로 채워지므로 칸 자체를 감점하지 않고, 칸에 들어갈 장소를 처음 보이는 장소로 본다. User Memory 의 생활 장소는 장소의 근거로 친다.
### 6.1 하루 흐름과 빠진 사건 — 20점
- 반영할 근거(이동, 활동·장소가 바뀌는 체류, 일정, 사진 장면, 하루의 일을 말하는 알림)가 최종 event 에서 빠지지 않았는가?
- 근거가 없는 이동·귀가·외출·활동 event 가 없는가?

- 하루를 읽을 수 있는 흐름인가? 대화가 아닌 event 가 10개를 넘지 않고, 근거 없이 몇 분짜리 조각으로 잘게 쪼개지지 않았는가?
### 6.2 사건 구성 — 20점
- 중복 event 가 없는가?
- 한 활동이 근거 없이 여러 event 로 갈리지 않았고, 다른 사건이 긴 event 안에 묻혀 사라지지 않았는가?
- 이동이 도착 뒤 활동과 구분되는가?
- 근거가 시간·장소가 맞는 event 에 붙어 있고 사진은 한 event 에만 있는가?
### 6.3 사실의 근거 — 20점
- event 의 사람·활동·음식·목적이 근거에서 확인되거나 사진 장면에서 합리적으로 추론되는가?
- 알림을 받은 것을 행동으로 바꾸지 않았고, 일정이 있었다는 것만으로 참석했다고 쓰지 않았는가?
- 대상 날짜와 다른 날·미래의 일정, 상대가 한 일을 사용자가 오늘 한 일로 쓰지 않았는가?
- User Memory 만으로 사건·참석·실명·관계를 확정하지 않았는가?
### 6.4 시간 — 10점
- event 가 window 안에 있고 시간순이며, 겹치는 event 는 한쪽이 다른 쪽을 감싸는 관계인가?
- 시간이 근거(일정·이동·체류·사진·결제 시각)와 맞고 근거 구간 밖으로 늘어나지 않았는가?

### 6.5 EventType — 10점

- 근거가 위치뿐인 체류에 활동 타입을 붙이지 않았고 `MEAL`·`REST` 에 그 근거가 있는가?
### 6.6 장소 — 10점
- 처음 보이는 장소가 그 event 의 근거(체류 장소·일정 장소·사진 속 상호·결제 가맹점·User Memory 의 생활 장소)와 맞고, 근거가 가리키는 이름이 있으면 그 이름인가?

- title 이 title 공통 규칙을 지켰는가?

## 7. User Memory — 100점
갱신 전 프로필과 이번 기록(dailyTimelines)으로 프로필을 고친 결과를 잰다. v3·v4 는 변경 목록(`changes`: item·action·reason·text)을 내고 코드가 끼워 넣는다. 변경 목록에 없는 항목은 그대로 보존되므로 바꾸지 않은 것으로 본다. v2 는 문서 전체를 내므로 기존 프로필과 달라진 항목을 변경으로 본다. v4 의 `places` 출력은 채점하지 않는다.
### 7.1 근거와 확인 정도 — 30점
- 바꾼 내용의 사실이 이번 기록이나 기존 프로필에서 확인되고 그 항목에 담을 만한가? 기록이 가리키는 데까지만 갔는가(나이·성별·직급 짐작 없음)?
- 추론은 `~로 보임`, 한 번 있던 일은 `한 번` 으로 적었고, 한 번 있던 일을 습관·취향으로 적지 않았는가?
- 성향·감정을 AI 가 쓴 title·subtitle 의 말투에서 읽지 않았고, memoryStyle 은 memo 만 근거로 했는가?
- memo·emotion 이 다른 기록과 어긋날 때 memo·emotion 을 따랐는가?
### 7.2 사람에 대한 정보 — 15점
- 그날의 업무·식사·이동을 일지처럼 옮겨 적지 않았는가?
- 기록이 분명히 알려 주는 새 사실(새 사람, 사는 곳·직장 변화, 반복된 활동, memo 의 평가)을 빠뜨리지 않았는가?
- 감정·사건을 날짜별로 나열하지 않았는가?
### 7.3 병합과 보존 — 25점
- 바꾼 항목에 그 변경과 상관없는 기존 문장이 그대로 남았고, 지우기만 하는 변경이 없는가?
- 같은 사람·주제를 한 문장으로 합쳤고, `한 번` 이 다시 나오면 반복으로 고쳤는가?
- 충돌은 그 문장만 고쳤고 하루의 예외를 충돌로 보지 않았는가?
- 뜻이 같은 변경이나 같은 항목을 두 번 낸 변경이 없고, `customAttributes` 키가 기존과 같은 글자인가?
### 7.4 항목 배치 — 15점
- 문장이 그 항목에 담을 내용과 맞고 헷갈리는 경계(routines 와 currentFocus, personality 와 values)를 지켰는가?
- 같은 정보를 두 항목에 적지 않았고, 고정 항목에 맞는 정보를 `customAttributes` 에 넣지 않았는가?
- 주변 사람의 정보를 사용자의 basicProfile 에 넣지 않았는가?
### 7.5 형식·크기·개인정보 — 15점
- 항목 500자·전체 5,000자 이내이고, `[크기]` 지시가 있으면 문장을 버리지 않고 줄였는가?
- 번호 값(전화·계좌·카드)·상세 주소·분 단위 시각·날짜가 없고 이름은 기록에 나온 그대로인가?
- 음슴체이고 출력 형식(변경의 항목·동작 값)이 맞는가?
