# 단계별 LLM-as-a-Judge 개편 (정량 메트릭 v5)

- 상태: 진행
- 관련 이슈:

## 배경·목표

지금은 트레이스 하나를 **한 번의 LLM 호출**로 채점한다(`judge-rubric` v4 · 7기준 0~10점 +
정량 Metric 20개). 최종 타임라인만 근거로 보기 때문에 "어느 단계가 망가뜨렸는지"를 짚지 못하고,
점수가 프롬프트 개선으로 이어지지 않는다.

새로 확정된 **라이모리 정량적 메트릭** 문서는 평가 대상을 파이프라인 단계별로 나누고 각 대상을
100점 만점으로 채점한다. LangFuse 로그도 단계별로 입력·출력이 그대로 남아 있으므로, 로그를
단계로 잘라 **단계마다 따로 LLM-as-a-Judge** 를 돌리는 구조로 전면 교체한다.

끝났을 때 참이어야 하는 것:

- Task 하나를 고르면 8개 평가 대상(Location·Calendar·Notification·Photo Event Agent,
  Timeline, Repair, Question, User Memory)이 각각 100점으로 채점된다.
- 각 채점은 **그 단계의 입력과 출력만** 근거로 받는다. 최종 타임라인 하나로 뭉뚱그리지 않는다.
- 메트릭 문서의 **항목과 확인 질문이 하나도 빠짐없이** 프롬프트로 전달되고, 결과에는 **항목마다
  점수와 이유**가 반드시 있다.
- 항목별 점수의 합이 총점과 항상 같다(코드가 계산해 보장).
- 감점 이유마다 입력 rawId · 출력 ID · field 경로가 남는다.
- 종합 스코어 = 채점 가능했던 대상들의 단순 평균(입력이 없는 대상은 N/A 로 제외).

## LangFuse 로그 구조 (2026-09-06 실물 확인)

### 트레이스

한 번의 API 호출이 트레이스 하나다. 이름이 곧 종류다.

| 필드 | 값 | 비고 |
| --- | --- | --- |
| `id` | 32자리 hex | LangFuse 고유 id. **taskId 와 다른 값** |
| `name` | `generate-timeline` \| `update-user-memory` | 평가 흐름이 갈리는 기준 |
| `session_id` | taskId | 2026-08 중순 이후 생겼다. **서버측 필터 가능** |
| `tags` | `['timeline']` \| `['user-memory']` | 서버측 필터 가능 |
| `metadata` | `{taskId, dailyRecordId, feature, scope…}` | taskId 가 여기에도 있다 |
| `input` | timeline: `{taskId, dailyRecordId, window, request{...}}` · user-memory: `{taskId}` | `request` 가 수집 원본 정본 |
| `output` | `{status, persisted, callbackSent, timedOut, partialSave, tokenRefreshCount, durationMs, tokenUsage, timeline}` | user-memory 는 `{status, repairAttempts, …, userMemory(해시만)}` |
| `environment` `release` `version` `latency` `total_cost` `scores` | — | `scores` 는 비어 있다(LangFuse 평가 미사용) |

`trace.input.request` 필드와 각 원본 항목의 키:

| 배열 | 항목 키 |
| --- | --- |
| `stays` | `rawId, startAt, endAt, latitude, longitude, place, address, places[], durationText` |
| `movements` | `rawId, startAt, endAt, start, end, durationText, distanceMeters, transports[]` |
| `calendars` | (표본 0건 — 반입 시 확인 필요) |
| `notifications` | `rawId, postedAt, appName, title, text` |
| `photos` | `rawId, takenAt, dateTaken, latitude, longitude, places[], address, description(최초 null)` |
| `healths` | `rawId, metric, startAt, endAt, value, durationMinutes` |
| `userMemory` | `contentCaptured(false), byteLength, sha256, schemaVersion, filledFieldCount, customAttributeCount` — **원문 없음** |

### 관측치(Observation)

트레이스 하나에 40여 개. 각 관측치의 필드는 다음과 같고, 단계 판정에 쓰는 것은 굵게.

`id` · **`parent_observation_id`**(트리) · **`type`**(SPAN·AGENT·CHAIN·GENERATION) · **`name`** ·
**`level`**(DEFAULT·WARNING·ERROR) · `status_message` · `start_time`/`end_time`/`latency` ·
**`input`** · **`output`** · **`metadata`** · `model` · `usage`/`usage_details` · 비용 필드.

**`metadata` 가 단계 식별자를 들고 있다.** 이름 문자열 매칭보다 이쪽이 안전하다
(툴 실행 관측치는 이름이 `execute-align_location_events()` 처럼 괄호까지 붙어 나온 사례가 있다).

- `agent`: `location` `calendar` `photo` `notification` `sleep_activity` `timeline` `repair` `question`
- `sourceStage`: `event` (Event Agent 5종에만)
- `iteration` / `maxIterations`: Repair 반복 번호
- `tool`: Repair 툴 실행(`lookup_source` `update_event` `align_location_events` …)
- `phase`: `initial`(최초 draft 확정) · `stage`: `FINAL` · `imageCount`: Photo vision 첨부 수

### 관측치 트리 (실행 순서)

```
SPAN  generate-timeline                        ← 트레이스 루트
├── SPAN  retrieve-source-snapshot             output.snapshot.sourceItems[]{rawId,itemType,startAt,endAt,payload}
├── SPAN  normalize-source-snapshot            output.request = 정규화된 수집 원본(= trace.input.request)
├── AGENT main-agent                           output.timeline = 최종 타임라인
│   ├── AGENT event-agent-location             {agent:location, sourceStage:event}
│   │   └── GENERATION infer-location-events
│   ├── AGENT event-agent-calendar
│   ├── AGENT event-agent-photo
│   │   ├── SPAN       download-photo-images
│   │   ├── GENERATION describe-photo-images   {imageCount:N}  ← vision 결과 정본
│   │   ├── GENERATION infer-photo-events
│   │   └── SPAN       photo-stage-counts
│   ├── AGENT event-agent-notification
│   ├── AGENT event-agent-sleep-activity       ← 문서에서 deprecated, 채점 제외
│   ├── CHAIN merge-event-results              output.mergedResult{candidates,fragments,warnings}
│   ├── AGENT timeline-agent                   output.timeline = draft
│   │   └── GENERATION generate-timeline-draft
│   ├── AGENT repair-agent                     output.timeline = repair 완료본
│   │   ├── SPAN  confirm-timeline-draft       {phase:initial}
│   │   ├── CHAIN analyze-repair-iteration     {iteration:N} output.plan{issues,toolCalls,done,summary}
│   │   │   └── GENERATION analyze-timeline-repair
│   │   ├── CHAIN execute-repair-plan          {iteration:N} output.results[]{tool,ok,message}
│   │   │   └── SPAN execute-<tool>            {tool:…} input.call{tool,args,reason}
│   │   │       └── (rerun_timeline_agent 이면 GENERATION generate-timeline-draft 재등장)
│   │   └── CHAIN confirm-repair-iteration     {iteration:N} output.timeline = 그 회차 결과
│   └── AGENT question-agent                   output.timeline.events[].question
│       └── GENERATION generate-event-questions
├── SPAN  store-timeline
├── SPAN  send-completion-callback
└── SPAN  finalize-timeline                    {stage:FINAL}
```

User Memory 트레이스는 훨씬 단순하다.

```
SPAN  update-user-memory                       output.userMemory = 해시만(사용 불가)
└── GENERATION update-user-memory-profile      input = [existing user memory]·[dailyTimelines] / output = 프로필 JSON 전문
```

### 한 실행 = 한 트레이스 (쪼개져 오지 않는다)

실제 파이프라인 실행 하나는 **`generate-timeline` 트레이스 한 건**으로 온전히 온다. 43개 관측치가
그 안에 트리로 들어 있고, 단계별 근거도 전부 그 안에 있다. User Memory 갱신만 별도 트레이스
(`update-user-memory`)로 따로 오고, 이건 taskId 가 달라 timeline 실행과 자동으로 이어지지 않는다.

다만 **수집 목록에는 조각난 이름의 트레이스가 훨씬 많다.** 이건 대상 서버의 **테스트 실행**이다.

| 구분 | 실제 실행 | 테스트 실행 |
| --- | --- | --- |
| 트레이스 이름 | `generate-timeline` (97건) · `update-user-memory` (6건) | `call-llm` 2599 · `analyze-repair-iteration` 2300 · `confirm-timeline-draft` 1873 · `main-agent` 1725 · `execute-repair-plan` 1290 · `confirm-repair-iteration` 1286 · `download-photo-images` 1022 · `photo-stage-counts` 683 · `describe-photo-images` 137 |
| taskId | UUIDv7 실제값 | `task-test` 고정(1688/1725) |
| total_cost | 평균 0.072 | **0** |
| latency | 평균 49s | 0.04s |
| 관측치 | 40여 개 트리 | 1~7개, 단계 하나 분량 |
| session_id·tags·metadata | 있음 | 전부 비어 있음 → **서로 이어붙일 수 없음** |

즉 수집분 13,018건 중 채점 대상은 **103건뿐**이고 나머지 99%는 테스트 노이즈다. Task 리뷰 목록에
`name ∈ {generate-timeline, update-user-memory}` · `total_cost > 0` · taskId 가 UUID 형식인 것만
남기는 필터가 필요하다(끄면 전체를 볼 수 있게 한다).

`agent: "a"`, `taskId: "task-test"`, 페이로드 1KB 같은 값이 보이면 테스트 실행이다. 채점하면
의미 없는 점수가 나온다.

### 이 구조에서 나오는 사실 다섯

1. **거의 모든 step output 에 그 시점의 `timeline` 스냅샷이 붙는다.** 그래서 단계별 전후 비교가
   가능하다. 반대로 그대로 저장하면 같은 타임라인을 수십 번 중복 저장하게 된다.
2. **`app/tasks/trace_builder.py` 가 지금 그 근거를 버린다.** `step.output` 의 `timeline` 키를
   무조건 제거하고 `step.input` 과 `generation.output` 은 저장하지 않는다. 단계별 채점의 전제가
   깨지므로 trace.json 계약부터 고쳐야 한다.
3. **`request.userMemory` 는 원문이 아니라 sha256·byteLength 뿐이다.** User Memory 원문은
   GENERATION 프롬프트의 `[user memory]` 블록과 user-memory 트레이스의 GENERATION 에만 있다.
4. **Event Agent 5종은 모두 같은 `request` 전문을 입력으로 받는다.** 자기 source 만 받는 게 아니다.
   따라서 채점 근거를 만들 때 **그 단계의 source 배열만 남기고 잘라야** "자기 입력만 보고 만들었는지"를
   잴 수 있다.
5. **최종 event 스키마가 바뀌었다.** 예전 로그는 `placeLabel` + 별도 `questions[]` 였는데, 최근
   로그는 `place` 이고 질문이 `events[].question` 으로 들어간다(`timeline.questions` 는 빈 배열).
   질문 생성률은 `events[].question` 으로 세야 한다. 현재 코드의 필드 힌트는 이미 낡았다.

## 범위 / 범위 밖

- 포함
  - 메트릭 문서를 저장소 정본으로 반입하고 단계별 rubric 프롬프트를 그 문서에서 만든다.
  - trace.json 을 단계 근거 보존 구조(v2)로 확장한다.
  - 단계별 근거 슬라이서 · 채점 스키마 · 총점 계산 · 병렬 실행.
  - Task 리뷰·채점 페이지와 채점 결과 페이지 재구성, 대시보드·개선책·개선 history·리포트 연동 전환.
  - User Memory(별도 트레이스) 채점 경로.
- 범위 밖
  - **문서의 "코드 측정" 항목을 결정론 코드로 계산하는 것**(아래 별도 절에서 결정 근거를 적는다).
  - Sleep / Activity Event Agent(문서에서 deprecated).
  - 모범 정답 Timeline 라벨링·정답 대조 채점(`모범 예시가 있으면 …` 조건부 기준은 근거가 없으면 N/A).
  - LangFuse 수집 방식·환경 구성 변경.

## 단계별 근거 scope 명세

채점 프롬프트에 들어가는 것과 **일부러 빼는 것**을 단계마다 못 박는다. 경로는 관측치 기준이고,
괄호 안은 그 관측치를 찾는 `metadata` 조건이다. 크기는 실측 JSON 문자 수(트레이스마다 다르다).

### 1. Event Agent 4종 — `event-location` `event-calendar` `event-notification` `event-photo`

| 구분 | 내용 |
| --- | --- |
| 관측치 | `AGENT` `{agent: <src>, sourceStage: event}` (≈12KB in / 0.3~15KB out) |
| 입력 | `input.request` 에서 **그 단계의 source 배열만** + `date` · `timezone` · `window`. Photo 는 여기에 `describe-photo-images`(GENERATION) 의 output(rawId→description)을 합쳐 vision 결과를 만든다 |
| 출력 | `output.result{candidates[], fragments[], warnings[]}` 전문 |
| 보조 | 하위 GENERATION `infer-<src>-events` 의 system·user 프롬프트(그 단계가 실제로 무엇을 지시받았는지) |
| 제외 | 다른 source 배열, `inputItemCounts`, `tokenUsage`, `durationMs`, 최종 타임라인, 다른 Agent 의 결과 |
| N/A | 해당 source 배열이 0건이거나 관측치가 없으면 채점하지 않는다 |

`candidate` 키: `eventType, timeRange{startTime,endTime}, title, description, evidenceSummary,
semanticTags[], places[], address, sourceRefs[], confidence, inferenceLevel, uncertainty`.
`fragment` 키: `sourceType, rawId, summary, timeRange`. `warning` 키: `agentName, message`.

### 2. Timeline Agent — `timeline`

| 구분 | 내용 |
| --- | --- |
| 관측치 | `AGENT` `{agent: timeline}` (≈26~37KB in / 7~11KB out) |
| 입력 | `input.request`(수집 원본 전체 + window) · `input.mergedResult{candidates,fragments,warnings}` |
| 출력 | `output.timeline`(draft) — `events[]` 전문 + `warnings[]` |
| 보조 | GENERATION `generate-timeline-draft` user 프롬프트의 **`[user memory]` 블록**(2.10 판정의 유일한 근거) |
| 제외 | Repair 이후 결과, 질문, `tokenUsage` |
| N/A | `timeline-agent` 관측치가 없거나 draft 가 비어 있으면 사유만 남긴다 |

### 3. Repair Agent — `repair`

| 구분 | 내용 |
| --- | --- |
| 관측치 | `AGENT` `{agent: repair, maxIterations}` (≈33~49KB in) |
| 입력 | `input.timeline`(수리 전 draft) · `input.eventResults`(Agent별 candidates·fragments) · `input.request` |
| 반복 근거 | 회차별로 ①`analyze-repair-iteration{iteration:N}.output.plan{issues,toolCalls,done,summary}` ②`execute-repair-plan{iteration:N}.output.results[]{tool,ok,message}` ③ 하위 `execute-<tool>` 의 `input.call{tool,args,reason}` · `level`(ERROR 면 실패) |
| 출력 | `repair-agent.output.timeline`(수리 후) |
| 제외 | **각 `execute-*` 관측치에 붙은 timeline 스냅샷 전문**(회차마다 15KB씩 중복). 대신 회차 종료본은 `confirm-repair-iteration{iteration:N}.output.timeline` 하나만, 그것도 이전 회차와 **달라진 event 만** 요약해서 넣는다 |
| N/A | `analyze-repair-iteration` 이 0회면 채점하지 않는다 |

3.1 의 `lookup_source` 호출 여부 판정은 `{tool: lookup_source}` 관측치의 존재·`args.rawId`·순서로 본다.

### 4. Question Agent — `question`

| 구분 | 내용 |
| --- | --- |
| 관측치 | `AGENT` `{agent: question}` (≈14KB) |
| 입력 | `input.timeline.events[]`(질문 붙기 전) + GENERATION user 프롬프트의 `[events]` 블록(**`timeOfDay` 가 여기에만 있다**)과 `[user memory]` 블록 |
| 출력 | `output.timeline.events[].question` 전부 + GENERATION `generate-event-questions` 의 output(`questions[]{clientEventId,question}`) |
| 제외 | 수집 원본 전체, candidates·fragments, Repair 이력 |
| N/A | event 가 0건이면 채점하지 않는다 |

### 5. User Memory Agent — `user-memory`

| 구분 | 내용 |
| --- | --- |
| 트레이스 | **별도** `update-user-memory` (`tags=['user-memory']`). timeline 트레이스와 taskId 가 달라 자동으로 이어붙지 않는다 |
| 관측치 | GENERATION `update-user-memory-profile` |
| 입력 | user 프롬프트의 `[existing user memory]` · `[dailyTimelines]` · 근거 안내 블록 |
| 출력 | GENERATION output 의 프로필 JSON(10개 자연어 field + `customAttributes`) |
| 제외 | `update-user-memory` SPAN 의 `output.userMemory`(해시·길이뿐) |
| N/A | GENERATION 이 없거나 output 파싱이 실패하면 채점하지 않는다 |

### 공통 규칙

- 근거는 **잘라내되 요약하지 않는다.** 남긴 부분은 원문 그대로 넣는다(문자열 길이 상한은 두지 않고,
  넣지 않기로 한 것만 뺀다). 지금 judge 도 `limit=None` 으로 전문을 넣고 있어 관행이 같다.
- 모든 단계에 공통으로 붙이는 머리말: `taskId` · `date` · `timezone` · `window` · 그 단계의
  `level`/`status_message`(실패 여부).
- 실패 트레이스(`trace.output.status != SUCCESS`, 관측치 `level=ERROR`)는 "실패했다"는 사실을 근거에
  적고, 산출물이 없는 단계는 N/A 로 둔다. 실패 자체를 0점으로 만들지 않는다.

  점수 작성 형식)과 **대상별 절**(1.1~1.5 / 2 / 3 / 4 / 5)을 뽑는다.
- 단계 rubric = 공통 preamble + 해당 절 **원문 전량** + 그 단계의 항목·배점 표. 첫 실행 때 프롬프트
  레지스트리에 `judge-stage-<stageKey>` 로 v1 이 등록되고, UI 에서 편집하면 기존 규칙대로 버전이 쌓인다.
- 기존 `judge-rubric` 은 남기되 신규 채점 경로에서는 쓰지 않는다.

### 2. rubric 전달 규칙 — 요약·발췌 금지

- 문서의 항목과 **`LLM 확인` 아래 확인 질문을 한 줄도 빼지 않고** 그대로 프롬프트에 넣는다.
  파서가 절을 통째로 옮기므로 사람이 항목을 옮겨 적을 일이 없고, 문서가 고쳐지면 프롬프트도 같이 바뀐다.
- 파서에 **누락 검사**를 건다: 각 단계 절에서 뽑은 표·불릿 수와 배점표의 항목 수가 맞지 않으면
  로딩 자체를 실패시킨다. "조용히 일부만 전달되는" 상태를 만들지 않는다.
- 출력 스키마가 **항목마다 `score` 와 `reason` 을 필수**로 요구한다(둘 다 빈 값 금지). 항목이 하나라도
  빠지면 스키마 검증에서 실패하고, `reason` 은 문서의 어느 확인 질문에서 감점했는지 적게 한다.
- 만점 항목도 이유를 적는다("무엇을 확인했고 왜 문제가 없었는지"). 이유 없는 만점을 막는다.

### 3. 단계 정의는 한 곳(`app/analysis/stages.py`)

배점표를 코드의 유일한 정본으로 둔다. 문서가 아직 `awaiting-human-review` 라 배점이 바뀌면 이 표만 고친다.

| stageKey | 대상 | 항목(배점) |
| --- | --- | --- |
| `event-location` | Location Event Agent | 공통 20(형식5·시간형식5·window5·source일치5) + 이동흐름20 · 체류병합15 · 이동수단10 · 장소활동15 · 제목설명10 · source처리10 |
| `event-calendar` | Calendar Event Agent | 공통 20 + 일정반영20 · 제목시간15 · EventType20 · 장소10 · 종일10 · 필수필드5 |
| `event-notification` | Notification Event Agent | 공통 20 + 유형판단15 · 메신저20 · 결제15 · 예약15 · noise10 · source보존5 |
| `event-photo` | Photo Event Agent | 공통 20 + 사진묘사25 · vision밖주장15 · 사진반영20 · cluster15 · source보존5 |
| `timeline` | Timeline Agent | 제목설명15 · 하루흐름15 · 병합25 · source반영12 · EventType8 · 시간8 · 장소5 · confidence2 · warning/memory10 |
| `repair` | Repair Agent | 입력이해15 · 문제발견25 · source별수정15 · tool선택20 · 관계없는수정20 · 완료요약5 |
| `question` | Question Agent | event근거20 · 회고유도30 · 표현20 · 전건생성20 · 고유성10 |
| `user-memory` | User Memory Agent | 근거구분20 · 갱신방식15 · field배치30 · field혼동15 · 크기개인정보20 |

각 stage 는 `evidence()`(근거 슬라이서)와 `trace_kind`(`timeline` | `user-memory`)를 함께 들고 있다.

### 4. 채점 결과 스키마와 총점 계산

- provider 의 strict JSON Schema 를 살리기 위해 stage 배점표에서 **stage 별 Pydantic 모델을
  동적으로 만든다**(`create_model`). 항목 키가 스키마로 고정되어 누락·환각이 안 생긴다.
- LLM 이 내는 것: 항목별 `score`·`applied`(평가할 입력이 있었는지)·**`reason`(필수)**,
  `deductions[]{itemKey, severity, description, sourceRefs[], outputPath}`,
  `alerts[]{kind, where, detail}`, `measurements[]`, `summary`.
- **총점은 LLM 이 아니라 코드가 계산한다**: `applied=false` 항목의 배점을 나머지 항목에 비례
  배분한 뒤 `round(Σscore / Σ배점 × 100, 1)`. 문서의 "항목별 합 = 총점" 불변식이 항상 성립한다.
- `alerts` 는 문서가 "점수와 별개로 명시"하라고 한 3종(입력에서 확인 안 되는 사실 생성 · 필수 반영
  source 누락 · 민감정보 검출)을 따로 담는다.
- N/A 처리: 해당 source 가 0건이거나 단계 관측치가 없으면 그 stage 는 채점하지 않고 사유만 남긴다.
  종합 평균에서도 빠진다(0점이 아니다).

### 5. "코드 측정"은 이번 범위에서 빼되, 자리는 남긴다

문서의 각 항목에는 `LLM 확인`과 `코드 측정`이 같이 적혀 있다. 이번엔 **결정론 코드로 계산하지 않는다.**

- 이유: 대부분의 코드 측정값이 "동일 사건", "필수 반영 source", "source 불일치 주장" 같은 **의미 판정**을
  분모·분자로 삼는다. 그 판정 자체가 LLM 몫이라, 코드가 계산하려면 판정 결과부터 받아야 한다.
  지금 만들면 "숫자는 있는데 그 숫자가 무엇을 세었는지 아무도 모르는" 지표가 된다.
- 그래도 **코드 측정 항목의 문장은 프롬프트에 그대로 전달한다.** 무엇을 세어야 하는지가 채점 기준의
  일부이기 때문이다. LLM 은 그 결과를 `measurements[]{name, value, numerator, denominator, reason}` 로
  적고, 셀 수 없으면 `null` 과 이유를 남긴다.
- 나중에 코드 계산을 붙일 자리는 계약으로 미리 열어 둔다. 문서 규칙 그대로 **"코드 측정값이 제공되면
  LLM 은 숫자를 다시 추측하지 않고 그 값을 사용한다"** 를 프롬프트에 넣고, 근거 조립 함수가
  `measurements` 입력을 받을 수 있게 인자만 만들어 둔다(이번엔 항상 비어 있다).

### 6. 근거의 원천은 trace.json (LangFuse 상세가 아니라)

지금 judge 는 SDK 객체를 직접 받는다. LangFuse 보존기간이 30일이라 그러면 과거 Task 를 다시
채점할 수 없다. 근거 슬라이서를 **정규화된 trace.json** 위에서 돌게 바꿔 스냅샷만 있으면 재채점이
되게 하고, 픽스처로 테스트도 쉬워진다. trace.json 은 다음을 더 담는다(`schemaVersion: 2`).

- 단계 정본 timeline: `timeline-agent` · `repair-agent` · `question-agent` · 회차별
  `confirm-repair-iteration` 의 결과만 남기고 나머지 통과 중복은 지금처럼 제거.
- `step.input` 추가 — 단, `request` 처럼 source 를 통째로 복제하는 부분은 `source.*` 참조로 치환.
- `generation.output` 추가(질문·사진 묘사·프로필 원문의 유일한 근거).
- `step.metadata`(agent·iteration·tool·phase)와 `level`·`statusMessage` 추가 — 단계 매핑의 기준.
- 반복되는 큰 값(프롬프트·타임라인 스냅샷)은 `process.blobs` 에 한 번만 담고 `…Ref` 로 가리킨다.

구버전 trace.json 은 단계 근거가 없으므로 "재수집 필요"로 안내한다.

**구현하며 바뀐 것**: 계획에 있던 `stages{}` 인덱스는 만들지 않았다. 단계 매핑을 trace.json 과
근거 슬라이서 두 곳에 두면 정본이 둘이 된다. 매핑은 `app/analysis/evidence.py` 가 `step.metadata`
로 그때그때 계산한다(비용이 없고 픽스처 테스트가 쉽다). 대신 blob pool 로 중복을 접었다
(실측 695KB → 296KB).

### 7. 실행과 캐시

- 단계별 실행 버튼과 "전체 채점" 버튼을 함께 둔다. 전체 채점은 ThreadPool 로 병렬(기본 워커 3,
  설정으로 조정)이고 진행 상황을 단계 표에 표시한다.
- 결과 캐시 키 = `(taskId, stageKey, rubric 버전, trace.json 해시)`. 같은 조건이면 다시 호출하지 않는다.

### 8. 저장 포맷과 기존 결과

`data/evaluations/<taskId>.json` 을 v2 로 바꾼다.

```json
{
  "schemaVersion": 2,
  "taskId": "...", "traceId": "...", "env": "dev", "name": "generate-timeline",
  "composite": { "score": 84.6, "stageScores": {"timeline": 78.0}, "skipped": ["event-photo"] },
  "stages": {
    "timeline": { "rubricRef": {"name": "judge-stage-timeline", "version": 1},
                  "judgedAt": "...", "scorecard": {} }
  }
}
```

기존 v4 레코드(`scorecard` 단일 카드)는 **읽기 전용**으로만 보여준다. 목록에서 `구버전` 뱃지를
달고 재채점·비교 대상에서 제외한다. 개선 history 는 새 종합 점수 기준으로 다시 쌓인다.

## 리스크·미결

- **호출량**: Task 하나에 최대 8회 LLM 호출(Repair 는 근거가 커서 가장 느리다). 완화 = 단계 선택
  실행 · 병렬 워커 · 캐시. Codex CLI 는 ChatGPT 계정 한도를 공유하므로 전체 채점을 남발하지 않는다.
- **프롬프트 크기**: 항목 원문을 전량 전달하므로 rubric 만 수천 자다. 근거까지 합치면 Repair·
  Notification 단계가 가장 크다(근거만 50KB 급). 넘치면 근거를 줄이는 게 아니라 **회차 요약·중복
  타임라인 제거**로 줄인다. 항목 문장은 줄이지 않는다.
- **보존 기간**: LangFuse 30일. 그 전에 trace.json v2 로 다시 저장해 두지 않으면 과거 Task 는
  단계별 재채점이 불가능하다. 개편 직후 최근 트레이스 재저장을 한 번 돌린다.
- **대상 서버 스키마 변화**: 최근에도 `placeLabel`→`place`, 질문의 위치가 바뀌었다. 슬라이서는
  두 형태를 모두 읽고, 못 읽으면 그 항목만 N/A + warning 으로 떨어뜨린다.
- **프롬프트 블록 이름 의존**: `[user memory]`·`[events]`·`[dailyTimelines]` 파싱은 대상 서버
  프롬프트가 바뀌면 깨진다. 위와 같은 방식으로 방어한다.
- **User Memory 표본**: 현재 수집분 6건, 상당수가 빈 프로필이다. 경로는 만들되 통계는 표본이 쌓인 뒤에 본다.
- **문서 상태**: 메트릭 문서가 `awaiting-human-review` 다. 배점·항목이 바뀌면 stage 배점표와
  `assets/rubrics/` 문서를 같은 커밋에서 함께 고친다.
- **미결**: Repair 반복(최대 3회)을 한 번에 채점할지 회차별로 나눌지. 1차는 전체 반복을 근거로
  한 번 채점한다.
