# 개선책 반영 상태 관리 + 개선 history 페이지

- 상태: 완료
- 관련 이슈:

## 배경·목표

개선책은 `data/improvements/<slug>.json` 에 저장되지만 **반영했는지·언제 반영했는지**를 남길
곳이 없다. 그래서 "이 개선책이 실제로 효과가 있었나"를 확인할 수 없다.

1. 기존 개선책 페이지에서 저장된 개선책의 **상태(미반영/반영/보류)와 반영 시기**를 관리한다.
2. 새 **개선 history** 페이지에서 반영된 개선책을 고르면, 반영 시기를 기준으로 **전후 지표를
   비교**해 실제로 좋아졌는지 보여준다.

## 데이터 현황 (구현 전 확인)

| 지표 | 출처 | 시간축 | 표본 |
| --- | --- | --- | --- |
| 건수·평균 latency·비용 | `collection.json` 행 | 행의 `timestamp` | 10,525 |
| 채점 점수·Metric | `evaluations/<taskId>.json` | **자체 시각 없음** → `taskId` 로 `collection.json` 조인 | 채점한 task 만 |
| 토큰 | `tasks/<taskId>/trace.json` 의 `operation.tokenUsage` | 위와 동일 | Page 2 에서 저장한 task 만 |

- 평가 파일에 시각 필드가 없다. 새로 넣지 않고 `taskId → 트레이스 timestamp` 조인으로 푼다.
  (평가는 언제든 다시 매길 수 있고, 비교의 기준은 "로그가 생긴 시점"이 맞다.)
- 트레이스 `name` 이 11종이고 단계마다 비용 규모가 다르다. 전체 평균만 보면 구성비 변화가
  개선 효과로 오해된다. **name 별 분해를 함께 보여준다.**

## 범위 / 범위 밖

- 포함: 개선책 레코드에 상태·반영시기·메모 추가(기존 파일 하위호환), 상태 편집 UI,
  history 페이지(전후 비교 표·추이 차트·표본 수 표기), 단위 테스트, 계약 문서.
- 범위 밖: 개선책 적용 자동화, 과거 로그 자동 재채점, 통계적 유의성 검정.

## 작업 분할

1. `app/improve/records.py` — 개선책 레코드 로드·정규화·상태 저장(정본).
2. `app/improve/compare.py` — 반영 시기 전후 집계(로그/점수/토큰), 일자별 추이.
3. `app/ui/improvement.py` — 저장된 개선책 목록 + 상태·반영시기 편집.
4. `app/ui/improvement_history.py` + `app/main.py` 등록 — 비교 화면.
5. `tests/test_improvement_history.py`.
6. `.agents/knowledge/domain/improvement-record.md` + Router 한 줄.
