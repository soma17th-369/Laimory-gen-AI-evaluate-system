# 채점 기준 v6 교체 — v3·v4 를 같은 기준으로

- 상태: 완료
- 관련 이슈:

## 배경·목표

대상 파이프라인 프롬프트가 v4 로 바뀌었는데 채점 기준(metric v5)은 v2 구조를 잰다. v4 는 문장만이
아니라 **단계 구성**이 바뀌었다.

- 위치·일정은 LLM 을 부르지 않고 코드가 만든다(`event-agent-location`·`event-agent-calendar` 없음).
- 사진·알림은 `clue-agent-photo`·`clue-agent-notification` 이 단서를 낸다. `metadata.agent` 는 v2 와
  같은 `photo`·`notification` 이지만 결과가 `output.result` 가 아니라 `output.clues` 에 있다.
- Timeline 은 `merge-event-results` 대신 프롬프트의 `[하루]`·`[근거 묶음]`·`[빈 시간]`·`[알림]` 을 읽는다.

그래서 지금 v4 를 채점하면 사진·알림·Timeline 이 **빈 근거로 채점돼 점수가 조용히 틀린다**.

목표는 v4 로 품질이 오른 것을 점수로 보이는 것이다. 그러려면 v3 와 v4 를 **같은 기준**으로 재야
한다. v4 만 새 기준으로 매기고 v3 의 v5 점수와 나란히 놓으면 "기준이 달라 오른 것"이라는 반박을
막을 수 없다. 끝났을 때 참이어야 하는 것:

- 기준은 v6 하나다(v5 를 교체한다). v1~v4 트레이스 모두 같은 v6 항목으로 채점된다.
- 근거 추출은 트레이스의 파이프라인 버전을 판별해 그 버전의 관측치에서 같은 의미의 근거를 꺼낸다.
- 채점 기록에 기준 버전(`metric`)과 파이프라인 버전이 남고, 종합 점수는 현재 기준의 단계만 센다.
- v3·v4 표본을 같은 기준·같은 채점 모델(Claude Opus)로 채점해 비교한다.

## 기준을 정하는 원칙

v6 는 **결과 품질**과 **두 버전이 공통으로 요구하는 제품 규칙**만 잰다.

- 버전 고유의 구현 방식은 채점하지 않는다: 출력 필드 모양(candidate·fragment ↔ 단서), 짧은 id,
  기본 event(E1…)·`mergeReason`·`placeCandidates` 같은 내부 구조.
- 한 버전에서 새로 바뀐 문체 규칙도 채점하지 않는다. 예: 제목이 v3 는 명사구, v4 는 음슴체이고
  v4 는 제목에 장소 이름을 쓰지 않고 문장에 `{place}` 칸을 쓴다. 어느 쪽도 깎지 않는다.
- 두 버전 공통 규칙은 그대로 잰다. 예: description 의 1인칭 평서형 과거형, 시간 표현·헤지·관찰자
  시점 금지, 근거가 말하는 만큼만 쓰기.
- 사용자가 정한 제품 방침은 버전과 무관하게 적용한다. 예: 사진으로 본 장면에서 행동을 추론하는 것은
  허용이다(기존 "Vision 결과 밖 주장" 감점은 이 방침과 충돌해 바꾼다).

## 범위 / 범위 밖

- 포함: 파이프라인 버전 판별, v4 근거 추출, Repair 의 "수정 전" 근거를 실제 입력(첫 확정본)으로 바로잡기,
  v6 기준 문서·단계표·보정 예시, **최종 타임라인 단계 신설**, 기록의 기준 버전, 화면·MCP·문서·테스트,
  v1~v4 표본 재채점과 비교.
- 범위 밖: 위치·일정 코드 결과를 결정론 검사로 재는 일(이번에는 최종 타임라인 단계가 그 결과를 함께 본다),
  비교 결과를 저장소 문서로 공개하는 일(내부 수치라 로컬에만 둔다).

## 접근

### 단계 구성 (v6)

| stageKey | 대상 | v2·v3 근거 | v4 근거 |
| --- | --- | --- | --- |
| `event-photo` | 사진 해석 | `event-agent-photo.output.result` + Vision 결과 | `clue-agent-photo.output.clues` + Vision 결과 |
| `event-notification` | 알림 해석 | `event-agent-notification.output.result` | `clue-agent-notification.output.clues` |
| `timeline` | Timeline 초안 | `merge-event-results` · 수집 원본 · `[user memory]` | 프롬프트의 근거 칸 · 수집 원본 · `[user memory]` |
| `repair` | Repair | 첫 확정본 · 회차별 계획·도구 · 수정 후 · 프롬프트 | 같음 |
| `question` | 질문 | 프롬프트 `[events]` · 출력 질문 | 같음 |
| `final` | 최종 타임라인(신설) | 수집 원본 · `[user memory]` · 사용자가 받은 최종 타임라인 | 같음 |
| `user-memory` | User Memory | `update-user-memory-profile` 입출력 | 같음 |

- `event-location`·`event-calendar` 는 뺀다. v4 에는 LLM 단계가 없어 두 버전을 같은 자로 잴 수 없다.
  위치·일정 품질은 `final` 이 사용자가 받은 결과로 함께 본다.
- `final` 을 둔다. v4 개선의 상당 부분이 코드(위치 뼈대·확정 단계)에서 나오므로, 사용자가 받은
  결과를 직접 재는 단계가 있어야 버전 비교가 결과 기준이 된다.
- 종합 점수는 지금처럼 채점된 단계의 단순 평균이다. 두 버전의 단계 구성이 같아 평균을 비교할 수 있다.

### 버전 판별

`clue` 단계(`metadata.sourceStage == "clue"`)나 `build-clue-bundles` 가 있으면 v4, 아니면 초안
프롬프트에만 있는 절 제목으로 v1·v2·v3 를 가린다. User Memory 트레이스는 갱신 프롬프트로 가린다.
판별 결과는 근거 요약과 채점 기록에 남긴다.

### 기록

단계 결과에 `metric`(기준 문서 버전)을 남긴다. 현재 기준이 아닌 단계 결과는 종합에서 빼고,
같은 Task 를 새 기준으로 채점하면 이전 기준 결과는 `previousMetric` 으로 옮겨 둔다(이력 jsonl 은 그대로).

### 비교 방법

- 채점 모델: Claude Opus(Claude Code CLI provider). GPT·Codex 는 쓰지 않는다.
- 표본: prod 의 v3 기간과 v4 기간에서 원본 구성(위치·사진·알림 유무와 개수)이 비슷한 날을 고른다.
  v4 첫날은 가벼운 기록이 많아 단순 평균이 구성 차이에 휘둘린다.
- 같은 근거를 두 번 채점해 채점 편차를 먼저 본다. 비교 차이가 편차보다 작으면 상승이라고 하지 않는다.
- v3 로그는 LangFuse 보존 기간이 지나면 사라지므로 채점 전에 `trace.json` 으로 먼저 받아 둔다.

## 리스크·미결

- 기준 문장을 어떻게 쓰느냐가 비교 결과를 좌우한다. 원칙(공통 규칙·결과 품질만)에서 벗어난 항목이
  없는지 사용자가 기준 문서를 한 번 본다.
- Repair 프롬프트는 길면 로그에서 잘려 온다(`contentPreview`). 잘린 경우 근거에 그 사실을 적는다.
- 채점자 편차가 커서 표본이 작으면 차이를 단정할 수 없다.
