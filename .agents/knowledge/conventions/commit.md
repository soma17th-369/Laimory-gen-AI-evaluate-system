# 커밋 관례

## 원칙

- commit·push 는 사용자가 요청하거나 승인한 경우에만 합니다.
- 변경을 **독립적으로 검토·되돌릴 수 있는 작은 작업 단위**로 나눕니다.
- commit 하나에는 **하나의 주된 목적**만 둡니다. unrelated refactor·formatting 을 섞지 않습니다.
- 다만 code 와 그에 필수인 test 를 억지로 분리해 중간 commit 을 실패 상태로 만들지 않습니다.
  (각 commit 은 그 자체로 통과 가능한 상태를 유지)

## 메시지 형식

```
type : 한글 설명
```

- `type` 은 아래 목록에서 고릅니다.
- 설명은 **무엇의 어떤 계약·동작을 바꿨는지 구체적으로** 적습니다.
  "수정", "업데이트" 처럼 뭉뚱그리지 않습니다.

### type 목록

| type | 쓰임 |
| --- | --- |
| `feat` | 새 기능·동작 |
| `fix` | 결함 수정 |
| `refactor` | 동작을 바꾸지 않는 구조 개선 |
| `docs` | 문서만 변경 |
| `test` | 테스트 추가·수정 |
| `chore` | 빌드·설정·의존성 등 잡무 |

> 목록에 없는 type 이 필요하면 먼저 확인하고, 확정되면 이 표를 갱신합니다.

## 예시

- `docs : AGENT.md 에 plan/worklog 작업 흐름 섹션 추가`
- `feat : 로컬 GUI 에 평가 실행 버튼과 진행 표시 추가`
- `fix : 빈 데이터셋에서 지표 계산이 0으로 떨어지던 경계 처리`
- `refactor : 지표 계산기를 evaluate 모듈로 분리`
