# 2026-08-20 — 개선책 반영 상태 + 개선 history

## 한 일

- 개선책 레코드에 `createdAt`·`status`·`appliedAt`·`note` 추가(예전 파일 하위호환).
- 개선책 페이지를 탭 2개로 나눠 `반영 상태` 탭에서 상태·반영 시기·메모를 편집·저장.
- 개선 history 페이지 신설. 반영된 개선책을 시간 순으로 놓고 구간마다
  전후 비교 표 · 기준별 점수 · 사용 모델 · 반영 이후 결과 목록 · 이름별 분해를 보여준다.
- 트레이스별 모델·토큰 롤업(`data/generations.json`)과 조회 버튼 추가.

## 결정과 근거

- **시간축을 평가 파일이 아니라 트레이스 timestamp 로 잡았다.** 평가 파일에는 시각 필드가 없다.
  새로 넣을 수도 있었지만, 평가는 언제든 다시 매길 수 있고 비교의 기준은 "로그가 생긴 시점"이
  맞다. `taskId` 로 조인하면 기존 파일도 그대로 쓸 수 있다.
- **구간은 개선책이 나눈다.** `[반영 시각, 다음 개선책 반영 시각)` 이고 비교 대상은 직전 구간.
  ±N일 같은 임의 창보다 "시간 순 나열" 요구에 맞고, 개선책이 겹쳐 섞이지 않는다.
- **점수는 task 당 한 번만 센다.** 한 taskId 에 트레이스가 여럿이라 그냥 세면 같은 평가가
  여러 번 반영된다.
- **표본 수(n)를 모든 값 옆에 붙였다.** 점수는 채점한 task, 토큰·모델은 상세 조회한 트레이스만
  가진다. 지금 데이터로는 구간당 채점 task 가 1개라, n 없이 평균만 보이면 근거 없는 숫자가 된다.
- **이름별 분해를 같이 뒀다.** 단계마다 비용 규모가 10배 이상 차이 나서, 전체 평균만 보면
  호출 구성비 변화가 개선 효과처럼 보인다.

## 막힌 점

- **모델·토큰이 트레이스 목록 API 에 없다.** `TraceWithDetails.observations` 는 관측치 id 목록
  뿐이다. GENERATION 관측치를 따로 조회(`observations.get_many`)해 traceId 별로 롤업하고
  `data/generations.json` 에 캐시했다. 트레이스당 API 1회라, 화면에 보이는 50건만 조회한다.
- 처음에 모델명을 `provided_model_name` → `model_id` 순으로 읽었더니 화면에 UUID
  (`4bf01a9f-…`)가 찍혔다. 실제 이름은 관측치의 **`model`** 필드(`gpt-5.4-mini`)에 있고
  `provided_model_name` 은 비어 있었다. 회귀 테스트로 고정했다.
