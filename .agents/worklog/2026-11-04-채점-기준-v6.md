# 2026-11-04 채점 기준 v6 교체

## 한 일

대상 파이프라인이 프롬프트 v4 로 바뀌었는데 채점 기준(metric v5)은 v2 구조를 재고 있었다. 기준을 v6 로
교체하고, v1~v4 트레이스를 같은 기준으로 채점할 수 있게 근거 추출을 버전별로 나눴다. 계획은
[2026-11-04-채점-기준-v6-교체](../plan/2026-11-04-채점-기준-v6-교체.md).

- `evidence.pipeline_version` 으로 트레이스의 프롬프트 세트를 가린다. v1·v2·v3 는 초안 프롬프트 첫머리가 같아
  각자에만 있는 절 제목으로 가린다. v2 첫 판(08-03)은 말투 절이 없어 융합 강령 절로 가린다.
- v4 근거: 사진·알림은 `clue-agent-*` 의 `output.clues`, Timeline 은 프롬프트의 한글 칸(`[하루]`·`[근거 묶음]`·
  `[빈 시간]`·`[알림]`). 칸 이름 정규식이 영문만 받아 한글 칸을 못 찾던 것을 고쳤다.
- Repair 의 "수정 전 draft" 를 Timeline 출력에서 첫 확정본(`confirm-timeline-draft` phase `initial`)으로 바꿨다.
  Repair 가 실제로 받는 것은 코드가 한 번 확정한 draft 다. 모든 버전에 해당하는 수정이다.
- 64KB 를 넘어 잘려 온 GENERATION 입력(`body.contentPreview`)에서 messages 를 되살린다. 전에는 잘린 트레이스의
  User Memory·프롬프트 근거가 통째로 비었다.
- 단계 구성: 위치·일정 단계를 빼고 `final`(최종 타임라인)을 더했다. 7단계.
- 채점 기록에 `metric`·`pipelineVersion` 을 남기고, 이전 기준 결과는 `previousMetric` 으로 옮겨 종합에서 뺀다.

## 결정과 근거

- **v4 만 새 기준으로 매기지 않고 v3 도 같은 기준으로 다시 채점한다.** 목표가 v4 로 오른 품질을 점수로 보이는
  것이다. v4 의 v6 점수를 v3 의 v5 점수와 나란히 두면 "기준이 달라 오른 것"이라는 반박을 막을 수 없다(사용자 선택).
- **기준은 결과 품질과 모든 버전 공통 규칙만 잰다.** 프롬프트 v3·v4 를 단계마다 대조해 공통 규칙과 한쪽 전용
  규칙을 갈랐다. 한쪽 전용 규칙 중 구현 방식(출력 모양·짧은 id·기본 event)과 문체 변경(제목 끝 모양, 제목의 장소
  이름, `{place}` 칸, 대화 문장 꼴, 질문의 장소 표현)은 채점하지 않는다. 그런 규칙을 넣으면 v3 가 구조적으로 깎여
  상승폭을 믿을 수 없다. 이 목록은 문서 머리말 「버전마다 다른 방식」 표로 모든 단계 프롬프트에 붙는다.
- **v5 항목 상당수가 v3·v4 둘 다와 어긋나 있었다.** 예: Timeline 문장을 해요체로 요구했지만 두 버전 모두 `~했다`
  이고 해요체를 금지한다. "집에서 시작해 집으로 끝나는 하루" 정의는 두 버전 모두와 반대다. Repair 는 v2 역할
  (원본 대조 재검증, 재구성 도구 선택)을 쟀다. User Memory 는 "routines 에 식사·회의를 모두 저장"하라고 했지만
  두 버전 모두 하루만 본 업무·식사·이동은 적지 말라고 한다. 이런 항목은 고치거나 뺐다.
- **사진 행동 추론은 허용한다(제품 방침).** v5 의 "Vision 결과 밖 주장" 감점을 지우고, 장면과 어긋난 행동과 사진이
  말하지 않는 신원·관계만 감점한다.
- **위치·일정을 단계에서 뺐다.** v4 는 코드가 만들어 LLM 단계가 없다. 같은 자로 잴 수 없는 단계를 남기면 종합
  평균의 구성이 버전마다 달라진다. 대신 `final` 이 사용자가 받은 결과를 재므로 코드가 만든 위치·일정의 품질도
  거기서 드러난다. v4 개선의 상당 부분이 코드에서 나오므로 결과 단계가 있어야 비교가 결과 기준이 된다.
- **질문 단계는 항목 키와 기준 순서를 유지했다.** `deterministic_checks` 가 coverage c01·c02 와 expression c02(40자)
  를 코드로 판정한다. 40자 규칙은 v3·v4 원문이 같다.
- **v5 문서는 이름을 v6 로 옮겨 내용을 교체했다.** 지난 본문은 git 이력과 프롬프트 레지스트리(`judge-stage-*`)에 남는다.
  위치·일정 판정 예시 두 파일은 단계와 함께 지웠다.
- **채점 모델은 Claude Opus(`claude-opus-5-5`, Claude Code CLI provider)다.** 사용자 지시. GPT·Codex 는 쓰지 않는다.

## 막힌 점 / 열린 질문

- 기준 문장을 어떻게 쓰느냐가 비교 결과를 좌우한다. 사용자가 v6 문서를 한 번 검토해야 한다.
- LangFuse 보존 기간을 단정할 수 없다(30일이 지난 dev 로그도 받아졌다). 비교 표본 트레이스는 채점 전에
  `trace.json` 으로 먼저 받아 두었다.
- 질문의 예·아니오형은 v3 만 명시적으로 금지하고 v4 는 단답형 예시가 있다. 공통인 "답하면 한두 문장의 기록이 된다"
  로만 판정한다.
- 대상 서버 설명 화면(`app/ui/pipeline_doc.py`)의 LangFuse 이름 표는 v2·v3 구조 그대로다. 채점과 무관해 이번에 두었다.

- v1 은 dev 에만 있고 질문 Agent 가 생기기 전 실행이라 질문 단계가 없다. 초안이 함께 내는 하루 단위 질문은
  채점하지 않는다(기준 문서 「버전마다 다른 방식」).
- 코드가 Repair 의 수정을 지운 경우까지 Repair 결과로 보일 수 있다. 근거에 코드가 되돌린 수정을 따로 보이면 막을 수 있다.

## 결과

- 같은 근거 반복 채점으로 단계별 편차를 먼저 본 뒤, 원본 구성이 비슷한 v1~v4 표본을 같은 기준·같은 채점 모델로
  채점해 비교했다. 비교 수치는 내부 자료라 저장소에 두지 않는다.
