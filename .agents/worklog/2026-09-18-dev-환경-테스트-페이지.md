## 결정과 근거

- **입력은 수집된 dev 트레이스의 원본 스냅샷에서 가져온다.** `normalize-source-snapshot.input.snapshot`
  이 테스트 요청과 거의 같은 모양이라(`timelineWindow.startTime/endTime` → `window.startAt/endAt`
  만 다름) 실제 하루치 입력을 그대로 다시 돌려 볼 수 있다. 최근 dev 트레이스 6건 모두 변환 후 검사
  오류 0건.
- **prod 트레이스는 목록에 넣지 않았다.** 운영 사용자 원본을 dev 서버로 보내는 것은 정책 판단이라
  dev 만 둔다.
- **`userMemory` 는 옮기지 않는다.** LangFuse 에는 해시만 남는다(`contentCaptured: false`).
- **itemType 은 막지 않고 경고만.** 서버는 itemType 이 있는지만 보고 값 종류는 제한하지 않는다. 서버
  `ItemType` 6개(`PHOTO CALENDAR STAY MOVEMENT HEALTH NOTIFICATION`) 밖의 값만 경고한다.
- **토큰이 없으면 헤더 없이 보낸다.**
- **자동 재시도 없음.** 한 번에 최대 약 150초와 LLM 비용이 들어서, 실패는 그대로 보여주고 사람이
  다시 누르게 한다. 같은 이유로 결과를 화면에만 두지 않고 파일로 남긴다.
- 검증은 스크래치 패드의 가짜 엔드포인트(명세 모양 200/502/401, Bearer 확인)로 했다. 실제 dev 서버
  호출은 주소를 받은 뒤 확인해야 한다.

## 막힌 점 / 열린 질문

- ~~명세 enum 에 `NOTIFICATION` 이 없다.~~ → **해결.** 처음 받은 명세 요약이 서버 enum 을 검색할 때
  마지막 값(쉼표 없는 줄)을 놓쳐 생긴 오류였다. 서버 `ItemType` 에 `NOTIFICATION` 이 있고 테스트
  엔드포인트도 받는다. 불러올 때 알림을 빼던 체크박스를 없애고 원본 항목을 전부 보낸다.
  - 알림 payload 는 `{appName, title, text}`. 한 시점 기록이라 `endAt` 은 넣지 않는다(원본의
    `endAt: null` 은 옮기지 않고, 값이 있으면 경고).
  - 운영 경로는 `title`·`text` 가 둘 다 없으면 400 으로 막지만 테스트 엔드포인트는 그대로 AI 로
    넘긴다 → 둘 다 비면 경고. 최근 dev 기록 알림 24건은 모두 `endAt` null, 둘 다 빈 것 0건.
  - AI 쪽이 알림을 실제로 처리하는지는 서버 저장소로는 확인할 수 없다(호출이 거절되면 AI 쪽 문제).
    운영 경로 LangFuse 기록에는 알림 단계(`event-agent-notification`)가 돌고 있다.
- **LangFuse 원본의 PHOTO `photoUrl` 이 `[REDACTED]` 다.** 트레이스에서 불러온 입력으로는 AI 가 사진을
  받지 못해 사진 판단이 시험되지 않는다. 검사에서 경고로 알린다. 실제 URL 이 필요하면 직접 넣어야 한다.
