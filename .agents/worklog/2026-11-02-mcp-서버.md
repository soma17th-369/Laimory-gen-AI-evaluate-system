# 2026-11-02 MCP 서버

## 한 일

이슈 #12 의 로컬 MCP 서버를 만들었다. 도구는 `sync_logs`, `list_logs`, `get_log`, `judge_task`, `get_job`
다섯 개이고, 구현은 `app/mcp_server.py`, 작업 표는 `app/tasks/jobs.py` 다. 계약은 `docs/MCP-명세.md`.

## 결정과 근거

- **`mcp` 2.x 의 `MCPServer` 를 쓴다.** `FastMCP` 는 2.x 에서 이름이 바뀌었다. 도구 파라미터 이름이 곧 공개
  계약이라 camelCase 로 두었다.
- **서비스 호출은 스레드에서 돌린다.** 이벤트 루프에서 돌리면 상세 조회가 호출 한도를 기다리는 동안 `get_job`
  까지 멈춘다.
- **작업 표는 메모리에만 둔다.** 서버가 끝나면 `jobId` 는 사라지지만 결과는 저장소에 남고 `get_log` 로 볼 수
  있다. 파일로 남기면 끝나지 못한 작업을 정리하는 일이 따로 생긴다.
- **연결이 끊기면 수집은 멈추고 채점은 끝까지 둔다.** 수집은 끝을 알 수 없고 이어받을 수 있다. 채점은 끝이
  정해져 있고 이미 비용이 든 일이다.
- **긴 수집은 20페이지마다 저장한다.** 프로세스가 강제로 끝나면 예외 처리도 돌지 않아 그때까지 받은 것을 잃는다.
- **채점 작업은 서버당 2건까지만 돌린다.** 한 건이 CLI 를 여러 개 띄우므로 요청을 받는 대로 돌리면 계정 한도와
  PC 자원을 금방 쓴다.
- **일부 오류는 코드만 돌려준다.** `INVALID_JUDGE_OUTPUT` 과 `SCHEMA_VALIDATION_FAILED` 메시지에는 LLM 출력이
  그대로 실린다. 채점 사유는 로그 원문을 인용할 수 있어서 응답으로 내보내지 않는다. 모르는 예외도 내용을 알 수
  없으므로 형식 이름만 낸다.
- **`findings` 는 `<log-content>` 로 감싼다.** 글 안의 닫는 태그가 표시를 벗어나지 못하게 치환한다.

## 확인한 것

- 명세의 연결 방식(`uv run --directory`)으로 실제 프로세스를 띄워 수집 → 선택 → 채점 → 결과 확인을 끝까지
  돌렸다. 실제 LangFuse 와 실제 LLM 을 썼고, 채점은 dev 로그 한 건의 `question` 단계 하나만 돌렸다. 저장은 임시
  폴더에 했고 결과가 `채점 결과` 화면에 보였다.
- 채점 도중 연결을 끊어도 끝난 단계와 `trace.json` 이 남았다.
- Claude Code 와 Codex 에 그 실행에만 쓰는 설정으로 서버를 붙여 도구 5개가 보이는 것을 확인했다. Codex 는
  모델 답으로, Claude Code 는 초기화 이벤트의 연결 상태로 확인했다.
- 명세의 타입 필드와 오류 코드를 코드와 기계적으로 대조했다.

## 막힌 점 / 열린 질문

- 밀린 양이 많으면 첫 `sync_logs` 가 수십 분 이상 걸린다. 호출 한도 때문이고, 화면 수집도 같다. dev 는 테스트
  실행이 많아 특히 오래 걸린다. 도구는 바로 응답하고 뒤에서 돌지만, 끝나기 전에 고르는 로그는 저장된 것까지만이다.
- 프로세스가 다르면 "같은 Task 채점 중"을 알 수 없다. 데이터는 안전하고 토큰만 두 번 든다.
