# 2026-09-06 단계별 LLM-as-a-Judge 개편

계획: [2026-09-06-단계별-llm-judge-개편.md](../plan/2026-09-06-단계별-llm-judge-개편.md)

## 왜 갈아엎었나

트레이스 하나를 한 번의 LLM 호출로 채점(`judge-rubric` v4 · 7기준 0~10점)하다 보니 "어느 단계가
망가뜨렸는지"를 짚지 못했다. 새 메트릭 문서가 평가 대상을 Agent 별로 나누고 각 100점으로 채점하게
정의해서, 로그도 단계로 잘라 단계마다 따로 채점하도록 바꿨다.

## 로그 조사에서 확인한 것 (실물)

- **각 단계의 입력·출력이 관측치에 그대로 있다.** 재구성 휴리스틱이 필요 없다. 단계 식별은 이름이
  아니라 `metadata`(`agent`·`sourceStage`·`iteration`·`tool`·`phase`)로 하는 게 안전하다 —
  툴 실행 관측치 이름이 `execute-align_location_events()` 처럼 나온 사례가 있다.
- **거의 모든 step output 에 그 시점 `timeline` 스냅샷이 붙는다.** 단계 전후 비교가 가능한 대신
  그대로 저장하면 같은 타임라인을 수십 번 담게 된다 → blob pool 로 접었다(695KB → 296KB).
- **`request.userMemory` 는 원문이 아니라 sha256·byteLength 뿐이다.** User Memory 원문은
  GENERATION 프롬프트의 `[user memory]` 블록과 user-memory 트레이스 안에만 있다.
- **Event Agent 5종은 모두 같은 `request` 전문을 받는다.** 그래서 근거를 자를 때 그 단계의 source
  배열만 남겨야 "자기 입력만 보고 만들었는지"를 잴 수 있다.
- **최종 event 스키마가 바뀌었다.** `placeLabel` → `place`, 질문이 `timeline.questions[]` 가
  아니라 `events[].question` 에 embedded 된다. 질문 생성률은 후자로 세야 한다.
- **수집 13,018건 중 채점 대상은 103건뿐.** 나머지는 대상 서버 테스트 실행(taskId `task-test`,
  비용 0, 관측치 1~7개, session_id·tags 없음)이라 목록 필터를 넣었다.
- `trace.session_id` = taskId, `metadata.taskId`, `tags` 가 생겨서 **서버측 필터가 가능해졌다**
  (2026-08 중순 이전 결론이 뒤집힘).

## 결정과 근거

- **총점은 코드가 계산한다.** LLM 은 항목별 점수·`applied`·이유만 낸다. 문서의 "항목 합 = 총점"
  불변식을 산수 실수 없이 지키고, 미평가 항목 배점 비례 배분도 코드가 한다.
- **항목 원문을 요약하지 않고 전량 전달한다.** 사용자 요구. 파서가 문서 절을 통째로 옮기고,
  `stages.criteria()` 가 문서에서 항목별 기준을 잘라 붙이고, `stages.validate()` 가 기준이 빈 항목을
  찾아내 조용한 누락을 막는다.
- **코드 측정은 이번 범위에서 뺐다.** 분모·분자가 대부분 의미 판정이라 코드가 세려면 그 판정부터
  받아야 한다. 문장은 그대로 전달하고 채점자가 `measurements` 로 적는다.
- **근거 원천을 trace.json 으로 옮겼다.** LangFuse 보존 30일이라 SDK 객체 의존을 끊어야 과거
  Task 재채점이 된다. 픽스처 테스트도 이 덕분에 가능해졌다.
- **`_strict_json_schema` 를 고쳤다.** 중첩 모델 필드에 `Field(description=...)` 을 주면 Pydantic 이
  `{"$ref": …, "description": …}` 을 만드는데 strict 모드가 거부한다(`$ref cannot have keywords`).
  `$ref` 옆 keyword 를 지우게 했다. 기존 단일 카드 모델도 같은 문제를 갖고 있었다.

## 실행 중 발견해 고친 것

- 채점자가 "평가할 장소 입력이 전혀 없다"면서 **0점**을 준 항목이 있었다. 문서 규칙상 그건 감점이
  아니라 미평가다. 채점자 지시에 "감점(0점)과 미평가(N/A)는 다르다"를 명시하고 예시를 넣었다.
- 예전 로그(`timeline.questions` 배열)에서 질문 근거가 비어 보이는 문제를 고쳤다. 지금 로그는
  `events[].question` 이라 embedded 우선, 없으면 배열로 떨어진다.
- **채점 기준을 항목에 묶었다.** 처음에는 문서 절을 통째로 프롬프트에 부었는데, 어느 기준이 어느
  배점에 속하는지 알 수 없었다. 이제 `배점표` + `항목별 확인 기준(원문)` 으로 나눠 넣고, 화면에도
  같은 표(항목·배점·확인 기준·코드 측정)를 그린다. 항목의 기준이 비면 로딩이 실패한다.
  문서의 항목은 heading 블록(`#### 이동 흐름 — 20점`)이거나 표 한 줄이라 둘 다 처리한다.
  표 항목은 marker 가 줄 가운데(LLM 확인 칸)에 있어서 자를 때 줄 처음으로 되감는다.
- **목록에 채점 여부를 넣었다.** `채점`(4/7 단계 · 미채점 · 구버전) · `종합` · `채점 시각` 을 맨 앞
  열로 두고, 상단 캡션에 채점 완료·구버전·미채점 건수를 적는다.
- **코드 측정을 걷어냈다.** 코드가 계산하지 않는데 채점자가 센 숫자를 받아 두는 건 검증할 수 없는
  값을 남기는 것이라, 프롬프트·결과 스키마(`measurements`)·화면에서 모두 뺐다. 문서 6장(텍스트
  출력 형식)도 JSON 스키마로 받는 지금 구조와 어긋나 프롬프트에서 뺐다. 프롬프트가 30% 짧아졌다.
- **배점표와 확인 기준을 하나로 합쳤다.** 배점이 항목 제목에 있으니 표를 따로 두면 같은 내용을 두 번
  읽게 된다.
- **채점자에게 가는 프롬프트는 화면에서 뺐다.** 대신 **채점 기준 설정** 페이지를 만들어 항목·배점·
  확인 기준을 표로 고치게 했다. 저장하면 `data/rubrics/<stageKey>.json` 이 그 단계의 채점 기준이
  되고(→ `stages.get()`), 프롬프트는 채점할 때마다 현재 항목으로 다시 만들어진다. 결과 스키마도
  항목 서명으로 캐시해서 항목을 추가·삭제하면 스키마가 따라간다.

## 화면 정리 (2026-09-07)

- **채점 기준을 Task 리뷰 안에서 고친다.** 단계마다 `기준 수정` 버튼 → 그 자리에서 항목 표를 편집.
  같은 편집기를 채점 기준 설정 페이지도 쓴다(구현 하나).
- **채점 결과 페이지는 실행 이력으로 바꿨다.** 근거를 다시 그리던 걸 없애 Task 리뷰와 역할이 겹치지
  않게 했다. 같은 단계를 여러 번 채점해도 덮어쓰지 않고 `history/<taskId>.jsonl` 에 한 줄씩 쌓이며,
  같은 Task·단계의 직전 점수와의 차이를 함께 보여준다.
- **점수와 무관한 기록 추가**: 대상 파이프라인이 쓴 값만 남긴다 — 그 단계의 토큰(입력/출력/합계)과
  실행 시간, Task 전체 토큰·시간·비용. 채점 자체의 토큰·시간은 남기지 않는다(필요 없다).
  Task 리뷰의 단계 표에도 `토큰`·`실행` 열을 넣었다.
- **채점 결과는 Task → 채점 실행 → 단계 3단계로 좁혀 본다.** 한 목록에 다 섞으니 어느 실행의
  점수인지 알 수 없었다. 한 번의 채점은 `runId` 로 묶인다(`전체 채점` 한 번 = 실행 하나).
- **이모지 제거.** 사이드바·페이지 제목·탭 아이콘·개선 history 의 색 동그라미까지 텍스트로 바꿨다.
