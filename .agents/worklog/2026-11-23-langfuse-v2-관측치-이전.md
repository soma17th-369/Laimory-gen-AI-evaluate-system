# 2026-11-23 — LangFuse 레거시 트레이스 API 제거 대응(v2 관측치로 이전)

## 배경

11/13 이후 prod 로그 수집이 `LANGFUSE_ERROR (status 410)` 로 멈췄다. 직접 불러 보니
`GET /api/public/traces` 와 `GET /api/public/traces/{id}` 가 둘 다 410 이고 본문이
`error: LANGFUSE_V3_API_REMOVED`, `Removed on 2026-11-16` 였다. 대신 쓰라는 것은
`GET /api/public/v2/observations` 를 `traceId` 로 묶어 쓰는 방식이다
(<https://langfuse.com/faq/all/deprecated-api-migration#traces>).

`list_generations` 가 쓰던 `client.api.observations.get_many` 는 SDK 4.14.3 에서 이미 v2
(`/api/public/v2/observations`)였다. 없어진 v1 은 `client.api.legacy.observations_v1` 쪽이라
이 함수는 영향이 없었다.

## 한 것

- `app/langfuse_client.py`
  - `list_observations` — v2 관측치를 커서가 없어질 때까지 받는다(빈 페이지에도 커서가 온다).
  - `list_traces(from, to, env)` — 구간의 루트 관측치로 트레이스 요약을 만들고, 비용이 0 보다 큰
    관측치만 따로 받아 `traceId` 별로 합친다. `has_traces` 는 구간에 루트가 있는지만 본다.
  - `get_trace` — 그 트레이스의 관측치를 전부 받아 예전 `TraceWithFullDetails` 와 같은 이름의
    필드(`TraceDetail`·`Observation`)로 묶는다. 입출력 JSON 문자열은 풀고, 트레이스 입력·출력은
    루트 것을 쓴다. 그래서 `trace_builder`·dev 테스트·테스트 데이터 화면은 고치지 않았다.
  - `Langfuse(tracing_enabled=False)` — 아래 "자기 호출 기록" 참고.
- `app/collect/sync.py` — 하루 구간을 오래된 쪽부터 훑는다. 증분은 커서보다 1시간 앞에서 시작하고,
  전체 수집은 첫 데이터 구간을 이분 탐색으로 찾는다. 병합할 때 처음 시각·taskId 는 저장본을 지킨다.
- 화면 진행 문구(페이지 → 구간), MCP 명세의 `pages` 설명, `collection-store.md` 갱신.
- 테스트: 수집은 구간 흉내로 다시 썼고, 조회는 v2 응답 흉내로 묶기·비용 합·루트 선택·입출력 풀기·
  커서 따라가기·추적 끄기를 본다.

## 결정과 근거

- **루트는 부모 id 가 아니라 `isRootObservation` 으로 찾는다.** 대상 서버 루트(`generate-timeline`
  등)는 상위 서비스 span 아래에서 시작해 부모 id 가 남아 있다. 문서의 "parentObservationId 가 null 인
  행" 규칙으로는 못 찾는다.
- **v2 는 늘 최신순이라 구간으로 오름차순을 만든다.** 정렬 인자가 없다. 한 번에 끝까지 최신순으로 받고
  끝에만 커서를 옮기는 방식도 있었지만, 개발 프로젝트는 하루 테스트 트레이스가 많아 메모리와 중단
  복구가 나빠져 접었다.
- **목록은 루트 입력을 받지 않는다.** 루트 입력은 원본 데이터 전체라 무겁다. taskId 는 세션 id 와
  같은 값이라(겹치는 구간에서 실제 실행 전부 일치 확인) 세션으로 충분하다. 세션이 없는 테스트 조각은
  taskId 가 비는데, 채점 대상이 아니고 예전에 저장한 값은 병합 때 지킨다.
- **비용은 `totalCost > 0` 인 관측치만 받는다.** 합에는 영향이 없고 비용 0 인 테스트 관측치를 건너뛴다.
- **증분 수집 1시간 앞당김.** 루트 span 은 끝날 때 전송된다. 예전 수집이 커서 앞쪽의 늦게 끝난
  트레이스를 놓친 사례가 비교에서 보였다.
- **처음 시각 유지.** 대상 서버 테스트가 7~8월 트레이스 id 를 재사용해 구간마다 새 루트가 붙는다.
  예전 목록은 처음 시각을 유지했으므로 같게 둔다.

## 확인한 것

- 겹치는 구간(레거시로 받아 둔 행 vs v2 로 만든 행): prod 는 전부 짝지어지고 이름·시각·user_id·비용·
  taskId 가 같았다. 다른 것은 시작=종료인 루트의 latency(v2 는 비움) 하나라 0 으로 맞췄다. dev 는
  세션 없는 테스트 조각의 taskId 와 위 latency 만 달랐다.
- 상세: 레거시로 저장된 `trace.json` 과 v2 로 다시 만든 것을 내용으로 비교했다. User Memory 는 바이트
  단위로 같았고, 타임라인은 ① `confidence` 의 `1` 대 `1.0` 표기(원본 문자열이 `1.0`) ② 같은 밀리초에
  시작한 루트·첫 자식의 순서 ③ 단계 안 생성 관측치 순서(예전엔 시각과 무관한 순서)만 달랐다.
  `statusMessage` 는 v2 가 빈 문자열을 줘서 예전처럼 null 로 맞췄다(채점 근거에 그대로 실린다).
- MCP 로 `sync_logs(prod)` → `get_job` done, prod 커서가 오늘로 넘어갔고, 11/16 이후 로그를
  `get_log` 로 열어 단계·근거가 나오는 것을 봤다.

## 자기 호출 기록

prod·dev LangFuse 에 `get_job`·`judge_task`·`get_log` 같은 이름의 TOOL 트레이스가 쌓여 있었다.
MCP Python SDK 가 도구 호출마다 `gen_ai.operation.name=execute_tool` 속성의 OpenTelemetry span 을
만들고, Langfuse 클라이언트가 전역 트레이서에 붙어 `gen_ai.*` span 을 기본으로 내보낸 것이다.
클라이언트를 환경마다 만들어 두 프로젝트 모두에 올라갔다. 이 도구는 LangFuse 를 읽기만 하므로
추적을 껐고, 끈 뒤 MCP 도구를 부른 시각 이후로 두 프로젝트에 TOOL 트레이스가 생기지 않았다.
이미 올라간 것은 지우지 않았다.
