# 2026-10-01 — 로그 수집이 LangFuse 호출 한도에 걸려 실패

## 배경

10월 1일 로그를 받으려고 "새 로그 동기화"를 눌렀더니 19페이지째에서
`ApiError 429 — Rate limit exceeded for GET /api/public/traces` 로 실패했다. 응답 본문이
`GET /api/public/v2/observations` 를 쓰라고 안내한다. 한도는 `x-ratelimit-limit: 5`,
`retry-after: 60` — 분당 5회이고 dev·prod 가 같은 한도를 나눠 쓴다.

실패하면서 그때까지 받은 1,900건도 저장되지 않았다. `sync()` 가 루프를 끝까지 돈 뒤에만
저장했기 때문이다. 문서(collection-store.md)는 "중간에 끊겨도 이어받는다"고 적고 있었지만
그건 `max_pages` 로 끊긴 경우에만 참이었다.

dev 에는 9월 13일 커서 이후 29,719건(대부분 Bedrock 테스트의 낱개 트레이스)이 밀려 있었다.

## 한 것

- `app/langfuse_client.py` — `list_traces` 가 429 를 만나면 `retry-after`+1초 기다렸다가 다시
  부른다(`_wait_on_rate_limit`, 최대 5번 대기). 다른 오류는 그대로 올린다.
- `app/collect/sync.py` — 조회가 예외로 끊기면 받은 행과 커서를 저장하고 예외를 다시 올린다.
  저장 부분을 `persist()` 로 묶어 정상 종료와 같은 코드를 쓴다.
- 테스트: `tests/test_collection_sync.py` 에 실패 후 이어받기 1건,
  `tests/test_langfuse_rate_limit.py` 신규 3건.
- `collection-store.md` 에 "중단 시 저장"·"호출 한도" 두 줄 추가.

## 결정과 근거

- **수집 방식은 바꾸지 않았다.** 한도를 기다리며 끝까지 받게만 했다. v2 관측치 API 로 옮기면
  훨씬 빠르지만(분당 30회, 한 번에 1,000건) 행 스키마의 `latency`·`total_cost`·`taskId` 를
  트레이스가 아니라 관측치에서 다시 만들어야 해서 별도 작업이다.
- **대기는 `langfuse_client` 에 둔다.** 한도는 LangFuse 호출의 성질이지 수집 규칙이 아니다.

## 확인한 사실 (v2 관측치 API)

- `/api/public/v2/observations` 한도는 분당 30회로 legacy 와 따로 센다.
- 응답 모양이 legacy 트레이스 상세와 다르다: `metadata` 키가 `scope.name` 처럼 점으로 펴져
  오고, `input`·`output` 은 JSON 문자열, 토큰은 `inputUsage`·`outputUsage`, 비용은 `totalCost`,
  모델 이름 필드는 비어 오고 `internalModelId` 만 온다.
- `traceId` 필터와 `fields=core,basic,time,io,metadata,model,usage,metrics,trace_context` 로
  트레이스 한 건의 관측치 전체를 한 번에 받을 수 있다.

## 열린 질문

- dev 에 하루 1,600건꼴로 테스트 트레이스가 쌓인다. 지금 방식으로는 하루치에 3~4분이 든다.
  수집을 v2 관측치 API 로 옮길지, 타임라인·유저메모리 트레이스만 받을지 정해야 한다
  (후자는 "필터 없음" 계약을 바꾼다).
